# Start Dispatch Desk in the cloud workspace

Use the existing checkout at `/workspace/aggroso`. Each cloud task is already isolated; do not create a Git worktree unless the user explicitly requests one. Preserve existing source, dependency declarations, lockfiles, environment files, and database data.

1. Use Node 24, then `cd /workspace/aggroso`. Set `npm_config_cache=/workspace/.npm-cache` if the host's default npm cache is not writable.
2. The install script installs npm dependencies, generates Prisma's client, and builds the frontend. If generation is blocked by the network policy, the required official domain is `binaries.prisma.sh`; keep checksum and TLS verification enabled. Resolve that before claiming the backend is ready.
3. For local development only, create `.env` from `.env.example` if `.env` does not already exist. Never overwrite existing configuration or log secret values. The example selects MockProvider and a loopback-only local PostgreSQL URL.
4. Run `docker compose up -d --wait` from the checkout to start PostgreSQL. Live containers may not survive snapshot restoration; the Compose volume retains local data when available. If the volume is not restored, initialization creates the seed workspace again; do not claim this preserves earlier local demo data without checking it.
5. Run `npm run db:migrate` and `npm run db:seed`. The seed is idempotent and preserves existing data.
6. Start the backend with `npm run dev` and frontend with `npm --prefix frontend run dev` in separate persistent command sessions. Backend is on port 8000 and Vite on 5173 by default. The production frontend is separately deployed to Vercel; do not publish or deploy without the user's instruction.
7. Check `GET /api/health` locally, then `GET /api/state` with a reviewer Bearer token if configured. Generate a draft through `POST /api/proposals` with a reason. Verify `currentVersion` and notifications remain unchanged until human approval. Do not approve an operational plan merely to start the environment.
8. Run `npm run test:unit` and `npm --prefix frontend run build`. For the full suite, use a dedicated PostgreSQL database whose name ends in `_test`, apply migrations there, and set `TEST_DATABASE_URL` before `npm test`. The API suite clears records in that test database. Never point it at the demo or hosted database.
9. `npm run test:browser` exercises the UI with stubbed HTTP. It does not replace the database-backed tests or prove a real OpenAI call works. It uses system Chromium where available; otherwise install Playwright's Chromium with its supported installer.
10. For real AI use `AI_PROVIDER=openai` and the existing secure `LLM_API_KEY` or `OPENAI_API_KEY` binding, with access to `api.openai.com`. Inspect names/presence only, never values. MockProvider is labelled and is valid for development/testing; the assessment's final hosted workflow requires operational OpenAI access.
